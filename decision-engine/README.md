# HadeelOS Decision Engine

TypeScript implementation of the [Decision Engine Specification v1](https://app.notion.com/p/399fe46cdbd081f0becee103be74f8bf) — the schemas, confidence calculator, decision lifecycle state machine, and `recalc()` function that power HadeelOS's Today Cockpit.

## Contents

- `src/types.ts` — Signal, SignalStore, EventLog, Decision, KGNode/KGEdge (Observation/Hypothesis/Belief/Decision record types), Hypothesis, Experiment, DigitalTwin, JournalEntry, MemoryGovernanceLog
- `src/confidence.ts` — `calculateConfidence()` implementing `Confidence = w1·SignalReliability + w2·HistoricalAccuracy + w3·CausalMaturityScore`
- `src/decisionStateMachine.ts` — the Decision state machine (`Proposed → Presented → Accepted/Rejected/Ignored → OutcomeRecorded`, with `Revised` looping back to `Presented`)
- `src/recalc.ts` — the formal `recalc()`, replacing the flat "+1% per accepted item" heuristic in the `today_cockpit` HTML prototypes with real confidence-weighted forecast and timeline ordering
- `tests/` — unit tests (vitest) for all of the above

## Usage

```bash
npm install
npm run typecheck
npm test
```

## Persistence layer (PR #2)

- `src/persistence/SignalStoreRepository.ts` / `EventLogRepository.ts` — storage-agnostic interfaces. Every method returns a `Promise`, and `EventLogRepository` has no update or delete method at all, so the append-only guarantee is enforced by the type signature, not just convention.
- `src/persistence/InMemorySignalStoreRepository.ts` / `InMemoryEventLogRepository.ts` — the initial backend. A future `PostgresSignalStoreRepository` / `PostgresEventLogRepository` implements the same interfaces; no call site elsewhere in the codebase needs to change.
- `src/persistence/clone.ts` — every entry is deep-cloned (`structuredClone`) at both the write boundary (`append`/`upsert`) and the read boundary (`getAll`/`get`/`findByDecisionId`). Without this, callers could mutate an object they passed in or got back and silently rewrite "immutable" history — the append-only guarantee has to hold for real, not just be the absence of an `update()` method.
- `append()` on `EventLogRepository` throws `DuplicateEventLogEntryError` for a repeated `id`, mirroring the primary-key constraint any real database-backed implementation will also enforce.
- `tests/persistence/*.contract.ts` — a reusable behavioral test suite per interface (`runSignalStoreRepositoryContractTests`, `runEventLogRepositoryContractTests`), including mutation-after-write and mutation-after-read cases and the duplicate-id case. Any new implementation's test file just imports the contract and calls it with its own factory — if it passes, the implementation is a verified drop-in replacement.
- Recording an outcome after the fact means **appending** a new `EventLogEntry` for the same `decisionId`, not mutating the original — `findByDecisionId` reconstructs the full history in insertion order. This mirrors the immutable-history guarantee already enforced by the Decision state machine (`OutcomeRecorded` is terminal, `supersedesDecisionId` links a new decision back to an old one).

## Application service (PR #3)

- `src/application/DecisionApplicationService.ts` — the **only** entry point that is allowed to call `SignalStoreRepository`, `EventLogRepository`, or `recalc()`. Nothing else in the codebase (and, later, the API layer) should reach past this class into the repositories or domain functions directly.
- `recalculateDay()` always runs in this fixed order: read the current signal store → upsert the incoming signal delta → read the effective signal store back from the repository → call `recalc()` **against that persisted effective store** → append one `EventLogEntry` per accepted decision. `recalc()` is deliberately called with `currentSignalStore: effectiveSignalStore` and an empty delta, never with the raw pre-persistence values — a real (e.g. Postgres) repository may normalize, clamp, round, or otherwise transform values on write, so recalc() and the Event Log snapshot must reflect what was actually saved, not what was asked to be saved. Nothing is written to the Event Log until `recalc()` has succeeded.
- `src/application/types.ts` — `RecalculateDayCommand` / `RecalculateDayResult` (the only shapes a future API/UI layer needs to know about), plus the injectable `IdGenerator` and `Clock` dependencies (with `RandomIdGenerator` / `SystemClock` as the real-usage defaults) that keep event IDs and timestamps out of the service's own hands so tests can be fully deterministic.
- `src/application/errors.ts` — `ApplicationError` and its subclasses (`SignalPersistenceError`, `EventLogPersistenceError`, `RecalcExecutionError`) so callers outside this package only ever need to handle one error hierarchy, never repository- or recalc()-specific failures directly.
- The service never returns repository internals: signal stores, forecasts, and ID lists returned from `recalculateDay()` are freshly built values, so mutating a result never mutates stored state.
- **Not atomic (v1):** the per-decision `EventLogEntry` appends happen in a loop, one repository call per decision. If an append fails partway through, the entries already appended remain persisted — there is no rollback. Callers must not assume `recalculateDay()` is all-or-nothing. True atomicity needs a real transaction boundary and is deferred to the PostgreSQL adapter PR.

## Knowledge Graph (PR #4)

- `src/knowledge-graph/KnowledgeGraphRepository.ts` — storage-agnostic contract for `KGNode`/`KGEdge`: `addNode`, `getNode`, `getNodesByDomain`, `addEdge`, `getEdge`, `findEdgesFrom`, `findEdgesTo`, `findEdgesBetween`, `updateEdgeMaturity`, `getMaturityHistory`. Node and edge IDs must be unique; an edge cannot reference a `fromNodeId`/`toNodeId` that was never added via `addNode()`; `confidence` must be a finite number in `[0, 1]`; `evidenceCount` must be a safe (non-fractional) integer `>= 0`; a self-edge (`fromNodeId === toNodeId`) is rejected unless the caller explicitly passes `{ allowSelfEdge: true }`.
- `src/knowledge-graph/InMemoryKnowledgeGraphRepository.ts` — the initial backend, deep-cloning (via `../persistence/clone`) at every read and write boundary, exactly like the Signal Store / Event Log repositories from PR #2. IDs and timestamps are never generated inside the repository — callers supply fully-formed values (see `KnowledgeGraphService` below), including a fully-formed `transition` object (`recordId` + `timestamp` + optional `reason`/`overrideMaturityTransition`) for `updateEdgeMaturity()`, so repository behavior stays deterministic and testable without faking the system clock or ID generation.
- **Numeric validation** rejects `NaN` and `+/-Infinity` outright (`confidence < 0 || confidence > 1` alone would silently admit `NaN`, since every comparison against `NaN` is `false`): `assertValidConfidence` requires `Number.isFinite(value)`, and `assertValidEvidenceCount` requires `Number.isSafeInteger(value)` so fractional evidence counts are rejected too. Applied identically in `addEdge()` and `updateEdgeMaturity()`.
- `src/knowledge-graph/CausalMaturityPolicy.ts` — the only place causal maturity transition legality is decided (`correlated → suspected_causal → experimentally_supported → stable_causal`). A single natural step forward is always allowed. Skipping more than one step requires `overrideMaturityTransition: true` **and** a `reason`. Any downgrade (moving to a lower maturity) requires a `reason` — there is no silent downgrade path.
- **Maturity transition history:** every successful `updateEdgeMaturity()` call — including a same-state ("no_change") reinforcement — appends one `MaturityTransitionRecord` (`id`, `edgeId`, `from`, `to`, `kind`, `previousConfidence`/`nextConfidence`, `previousEvidenceCount`/`nextEvidenceCount`, `reason`, `overrideUsed`, `timestamp`) to an append-only, per-edge, deep-cloned history, mirroring the `EventLogRepository` pattern from PR #2: no update or delete method exists for these records. A failed validation (invalid confidence/evidenceCount, a disallowed maturity transition, or a duplicate `recordId`) writes nothing — neither the edge nor the history changes. `getMaturityHistory(edgeId)` returns the full trail in insertion order (an empty array for an edge with no history yet, or for an unknown edge id — it never throws). Previously, transition legality was validated but the outcome was never persisted anywhere, so there was no way to audit *why* an edge's maturity had changed; this closes that gap.
- **`MaturityTransitionRecord.id` uniqueness:** `updateEdgeMaturity()` rejects a `transition.recordId` that already identifies a record on *any* edge — not just the edge currently being updated — via `DuplicateMaturityTransitionRecordError`, checked before either the edge or the history is written. This mirrors `EventLogRepository`'s `DuplicateEventLogEntryError` guarantee from PR #2 and anticipates the `kg_maturity_history` table's primary key once a real database backend exists. (Flagged during PR #5 review as a gap in the PR #4 in-memory implementation; fixed here rather than deferred, since it was a small, self-contained change.)
- `src/knowledge-graph/KnowledgeGraphService.ts` — thin orchestration layer with injected `IdGenerator`/`Clock` (reusing the same interfaces from `src/application/types.ts`), so it's the only place that constructs `KGNode`/`KGEdge` IDs and timestamps, including the `recordId` for each maturity-transition record. Nothing outside this service should call `KnowledgeGraphRepository` directly. `getMaturityHistory()` is exposed as a thin passthrough so callers never need to reach past the service to read the audit trail.
- `tests/knowledge-graph/knowledgeGraphRepository.contract.ts` — reusable behavioral test suite (`runKnowledgeGraphRepositoryContractTests`), covering duplicate IDs, missing node references, invalid confidence/evidence (including `NaN`/`Infinity`/`-Infinity`/fractional evidenceCount), the self-edge rule, every maturity-transition case (natural step, rejected skip, allowed override-with-reason, rejected silent downgrade, allowed downgrade-with-reason), the full maturity-history audit trail (reason persisted on downgrade, `overrideUsed: true` on override, `reason: null` on a natural advance, a same-state reinforcement recording an event, stable insertion order across multiple updates, mutation-safety of returned records, and "failed validation writes nothing"), the two `DuplicateMaturityTransitionRecordError` cases (same edge, and cross-edge global uniqueness), defensive cloning, and insertion/query order. Any future `PostgresKnowledgeGraphRepository` test file just imports and calls this contract with its own factory.

## Learning Engine (PR #5)

- `src/learning/HypothesisRepository.ts` / `InMemoryHypothesisRepository.ts` — storage-agnostic contract and in-memory backend for `Hypothesis` records, mirroring every other repository in this codebase: `add`, `get`, `getByRelatedEdgeId`, `updateStatus`. Deep-cloned at every read/write boundary; `confidence`/`evidenceCount` validated with the same `Number.isFinite()`/`Number.isSafeInteger()` rules established in PR #4.
- `src/learning/HypothesisStateMachine.ts` — the only place a Hypothesis status transition is decided. Exactly three lifecycle paths are allowed: `forming → testing → confirmed`, `forming → testing → rejected`, and `forming → unknown_competing`. `confirmed`, `rejected`, and `unknown_competing` are terminal.
- `src/learning/ExperimentRepository.ts` / `InMemoryExperimentRepository.ts` — same pattern for `Experiment` records: `add`, `get`, `findByHypothesisId`, `updateStatus`. `add()` enforces the full guardrail field list (below); `updateStatus()` enforces both the structural lifecycle and the consent guardrail, and refuses any update once an experiment has reached a final status (`ExperimentImmutableError` — a completed experiment is immutable).
- `src/learning/ExperimentStateMachine.ts` — the purely structural lifecycle graph, the same for every experiment regardless of category: `proposed → awaiting_consent → baseline → running → washout → evaluated → confirmed / rejected / inconclusive`, with `aborted` reachable from any non-final status. `proposed → baseline` is also structurally valid — it's `ExperimentPolicy`'s job to block it for regulated categories.
- `src/learning/ExperimentPolicy.ts` — everything that isn't purely structural: the guardrail field checklist every experiment needs (`hypothesisId`, `intervention`, `singleVariable`, `durationDays`, `baselinePeriodDays`, `successMetric`, `stopRule`, `washoutPeriodDays`, `category`), the consent gate (`health`/`financial` experiments can never skip `awaiting_consent`, and leaving `awaiting_consent` for `baseline` always requires `consentGiven: true`, for every category), and the proof rules: a single confirmed experiment can promote an edge to at most `experimentally_supported`; `stable_causal` requires a documented minimum of confirmed experiments and elapsed days, consistent results, and no unresolved competing hypothesis (`qualifiesForStableCausal`).
- `src/learning/EvidenceEvaluator.ts` — deterministic mapping from a run's evidence (`effectObserved`, `metricMet`) to an outcome: no effect observed → `rejected`; effect observed and the pre-declared success metric met → `confirmed`; effect observed but metric not met → `inconclusive` (insufficient).
- `src/learning/HypothesisService.ts` / `ExperimentService.ts` — the orchestration boundary for this module, with injected `IdGenerator`/`Clock` (reusing `src/application/types.ts`). `ExperimentService.evaluate()` is the one place a confirmed experiment's result is connected back to its Hypothesis (moves it to `confirmed`) and to the Knowledge Graph edge (`relatedEdgeId`): it aggregates every confirmed experiment across every hypothesis tied to that edge to decide the resulting maturity, and calls `KnowledgeGraphService.reinforceEdge()` with `overrideMaturityTransition: true` only when the jump is more than one step (e.g. `correlated → experimentally_supported` on a first confirmed experiment) — never to reach `stable_causal` in a single step from below `experimentally_supported`, so an edge can never go from `correlated` straight to `stable_causal` no matter how strong one experiment's result is.
- `src/knowledge-graph/KnowledgeGraphService.ts` gained a `getEdge()` read passthrough in this PR, so `ExperimentService` can read an edge's current maturity/confidence before reinforcing it without reaching past `KnowledgeGraphService` into `KnowledgeGraphRepository` directly.
- `src/types.ts`'s `Experiment` gained a `consentGiven: boolean` field (previously only `requiresExplicitConsent` existed) — the explicit record of whether consent was actually granted, as opposed to whether it's required.
- `tests/learning/hypothesisRepository.contract.ts` / `experimentRepository.contract.ts` — reusable behavioral test suites, same pattern as `knowledgeGraphRepository.contract.ts`. Plus dedicated unit tests for both state machines, `ExperimentPolicy`'s guardrails/consent/proof rules, `EvidenceEvaluator`, and both services (including an end-to-end `ExperimentService` test proving an edge reaches `stable_causal` only after enough confirmed experiments/days accumulate, and stays capped at `experimentally_supported` while an unresolved competing hypothesis exists).

## Digital Twin + Memory Governance (PR #6)

- `src/types.ts` gained `DigitalTwinSnapshot` (`id`, `userId`, `derivedAt`, `stress`, `energyCurve`, `decisionStyle`, `behaviorPatterns`, `knownPreferences`, `activeConstraints`, `sourceVersions`) and `MemoryRecord`/`MemoryGovernanceRecord` (`MemoryState`: `Missing`/`Learning`/`Knows`; `MemoryRegressionReason`: `evidence_decay`/`stale_data`/`contradiction`/`user_correction`/`user_forget`/`experiment_opt_out`/`source_disabled`/`unreliable_source`) — deliberately kept separate from the pre-existing, lighter `DigitalTwin`/`MemoryGovernanceLogEntry` types, which `recalc()` and the Application Service already depend on and which this PR does not touch.
- `src/twin/DigitalTwinRepository.ts` / `InMemoryDigitalTwinRepository.ts` — storage-agnostic contract and in-memory backend for the append-only `DigitalTwinSnapshot` history (`save`, `getById`, `getLatest`, `getHistory`), following every convention established since PR #2: `Promise`-returning methods, deep-cloning at every read/write boundary, `DuplicateDigitalTwinSnapshotError` on a repeated id.
- `src/twin/TwinDerivationPolicy.ts` — the only place a Digital Twin's fields are actually computed, as pure, deterministic functions: `deriveStress` (from `mood_score`/`sleep_quality`, `"unknown"` when either is missing — never silently defaulted to `"low"`), `deriveEnergyCurve` (a fixed set of hours, each with `expectedEnergy`/`confidence` derived from `sleep_duration`, never the raw signal value itself), and `deriveDecisionStyle`/`deriveBehaviorPatterns`/`deriveKnownPreferences`/`deriveActiveConstraints` (from `Knows`, unblocked `MemoryRecord`s only — a blocked or not-yet-`Knows` memory is excluded even if the caller passes it in, so "blocked memory never enters the Digital Twin" holds regardless of what upstream code does).
- `src/twin/DigitalTwinService.ts` — thin orchestration layer with injected `IdGenerator`/`Clock`; the only place that constructs a snapshot's `id`/`derivedAt` and the only caller of `DigitalTwinRepository`. `deriveAndPersist()` never stores a raw `Signal` or `SignalStoreEntry` — every persisted field passes through `TwinDerivationPolicy` first.
- `src/memory/MemoryStateMachine.ts` — the structural lifecycle `Missing -> Learning -> Knows`, with regression `Knows -> Learning -> Missing`, mirroring the KG causal-maturity / Learning Engine state-machine pattern. Two explicit, narrowly-scoped overrides exist, each requiring the caller to also record a `reason`: `forceCollapse` (`Knows` straight to `Missing`, reserved for `MemoryDecayPolicy`'s `"stale_data"` case) and `userCorrection` (any state straight to `Knows`, reserved for `MemoryGovernanceService.correct()` — a direct user statement doesn't have to earn its way through `Learning` the way accumulated system inference does).
- `src/memory/MemoryDecayPolicy.ts` — deterministic, pure `evaluateDecay(memory, now)`: no regression before `DECAY_THRESHOLD_DAYS` (30) since `lastReinforcedAt`; one-step regression with reason `"evidence_decay"` after that; a forced collapse straight to `Missing` with reason `"stale_data"` after `STALE_THRESHOLD_DAYS` (90). Never reads the system clock itself — `now` is always caller-supplied.
- `src/memory/MemoryRepository.ts` / `InMemoryMemoryRepository.ts` — same atomic state-plus-audit-log pattern as `KnowledgeGraphRepository.updateEdgeMaturity()`: `updateState()` validates confidence/evidenceCount/transition legality, then writes the updated `MemoryRecord` and appends exactly one `MemoryGovernanceRecord` to an append-only, per-memory, deep-cloned log in the same call. `MemoryGovernanceRecord.id` uniqueness is enforced **globally**, across every memory's log, via `DuplicateMemoryGovernanceRecordError` — the same discipline just retrofitted onto `KnowledgeGraphRepository.MaturityTransitionRecord.id` earlier in this PR cycle, built in here from the start instead of deferred.
- `src/memory/MemoryGovernanceService.ts` — the only orchestration boundary allowed to call `MemoryRepository.add()`/`updateState()`: `createMemory`, `reinforce` (one promotion step per call — evidence has to accumulate to reach `Knows`, no shortcut), `correct` (user-authored, `confidence: 1`, uses the `userCorrection` override), `forget` (resets to `Missing` **and** sets `blocked: true`, so a forgotten fact stays excluded from every future Digital Twin even if the system re-learns it later), `blockInference`/`unblockInference` (toggle `blocked` without touching state or value), `applyDecay` (a no-op — no write, no governance record — when nothing is due), `applyContradiction`, `optOutExperiment`, `demoteForSourceIssue`.
- `src/memory/MemoryMapService.ts` — the read-only counterpart: `getMemoryMap` (everything, for "what does the system know about me"), `getKnownMemories` (`Knows` and not blocked — what `DigitalTwinService` should prefer as its memory input), `getGovernanceLog`. Nothing outside these two services should call `MemoryRepository` directly.
- `tests/twin/digitalTwinRepository.contract.ts` / `tests/memory/memoryRepository.contract.ts` — reusable behavioral test suites, same pattern as every other `*.contract.ts` file in this codebase. Plus dedicated unit tests for `TwinDerivationPolicy` (including an explicit no-raw-signal-leakage assertion against a marker value that must never appear in a persisted snapshot), `MemoryStateMachine`, `MemoryDecayPolicy`, `DigitalTwinService` (deterministic derivation across independent service instances, blocked-memory exclusion, cloning safety), and `MemoryGovernanceService` (the full `Missing -> Learning -> Knows` promotion path, correction, forget, block/unblock, decay, stale-data force-collapse, contradiction, cloning safety).

## Counterfactual Engine (PR #7)

- `src/counterfactual/Scenario.ts` — `buildScenarios(candidateDecisions)` builds one `Scenario` per candidate `Decision`, in input order. v1 evaluates exactly one decision per scenario (`decisionIds` always has length 1) — `candidateDecisions` are treated as mutually exclusive options for the same decision point (e.g. different times/actions for `gym_time`). `decisionIds` is kept as an array so a future version can evaluate combinations of decisions accepted together without changing the shape.
- `src/counterfactual/ScenarioEvaluator.ts` — `evaluateScenario()` is a pure, deterministic function of a `Scenario` and a `ScenarioEvaluationContext` (twin, signals, a `KnowledgeGraphSnapshot`, historical accuracy, baseline forecast). It never reads the clock, never generates an ID, and never mutates its inputs. `KnowledgeGraphSnapshot` is a plain, pre-computed view of the relevant Knowledge Graph edges (`edgesByDecisionType`) — the caller (the future `TodayDecisionApplicationService`, PR #8) builds it from `KnowledgeGraphRepository`, so this engine never depends on the live repository and stays trivially deterministic. A decision type's causal-maturity contribution is discounted by the strongest matching edge's own `confidence`, so a low-confidence relation can never act as a strong reason on its own. Each `ScenarioResult`'s `contributors` are normalized to sum to 1 (or 0 when every source is empty), so their relative weight is directly inspectable.
- `src/counterfactual/UncertaintyPolicy.ts` — `evaluateScoreUncertainty()` compares the top two ranked scenario scores. A gap under `NEAR_TIE_SCORE_THRESHOLD` (0.03) is reported as `{ isUncertain: true, reason: "near_tie", margin }` instead of picking a confident winner — a near-tie is treated as a real epistemic state, not rounding noise.
- `src/counterfactual/ExplainAlternatives.ts` — `buildExplanation()` derives every `selectedBecause`/`rejectedBecause` string directly from a `ScenarioResult`'s own `contributors` (its strongest contributors for the winner, its weakest plus the score gap for each alternative) — never a separately hand-written string, so the explanation can never drift from the numbers that actually drove the outcome.
- `src/counterfactual/CounterfactualEngine.ts` — `runCounterfactualEngine()` is the single entry point: builds and ranks scenarios, decides uncertainty, and assembles the explanation. Two cases are handled as clear, well-formed results rather than exceptions: an empty `candidateDecisions` list (`selectedScenario: null`, `uncertainty.reason: "no_candidates"`) and an empty `signals` store (`uncertainty.reason: "missing_signals"` — scenarios are still computed and returned as `alternatives` so a caller has something to show, but no confident winner is selected). The whole engine is a pure function: identical input always produces identical output, and no input object is ever mutated.
- `src/counterfactual/errors.ts` — `CounterfactualError` / `CounterfactualComputationError`, reserved for genuine internal-consistency failures. The expected degenerate cases above are not errors — see `CounterfactualEngine.ts`.
- `tests/counterfactual/` — `counterfactualEngine.test.ts` covers determinism, no-mutation, empty candidates, missing signals, a low-confidence-graph comparison, tie/near-tie/wide-gap uncertainty, bounded probabilities, contributor normalization, and explanation consistency, exactly matching the required test list. `scenarioEvaluator.test.ts`, `uncertaintyPolicy.test.ts`, and `explainAlternatives.test.ts` cover each pure function in isolation.

## Status

Implements the schemas, pure functions, in-memory persistence layer, the Application Service, the Knowledge Graph persistence layer, the Hypothesis/Experiment Learning Engine, the Digital Twin / Memory Governance module, and the Counterfactual Engine from the spec. Not yet wired to a real database (Postgres) or Decision Orchestration v2 (connecting the Counterfactual Engine into the Application Service) — those are the next milestones.

## Design notes from review

- `recalc()` takes both `currentSignalStore` (the full known state) and `signalStoreDelta` (what changed since the last pass), and merges them before computing confidence. Using the delta alone would zero out confidence during a quiet period with no fresh signals, even though the system's last-known state is still valid.
- `SignalType` is `KnownSignalType | \`custom:${string}\`` rather than `KnownSignalType | string` — the latter silently widens the whole union to `string` and defeats type-checking.
- `OutcomeRecorded` is a terminal state. A decision whose outcome has been logged is closed history and is never rewritten. If new signals change the recommendation afterward, a new `Decision` is created with `supersedesDecisionId` pointing back to the original, instead of transitioning it to `Revised`.
- CI (`.github/workflows/decision-engine-ci.yml`) runs `npm ci`, `npm run typecheck`, and `npm test` on every PR touching this package.
