# HadeelOS Decision Engine

TypeScript implementation of the [Decision Engine Specification v1](https://app.notion.com/p/399fe46cdbd081f0becee103be74f8bf) — the schemas, confidence calculator, decision lifecycle state machine, and `recalc()` function that power HadeelOS's Today Cockpit.

## Contents

- `src/types.ts` — Signal, SignalStore, EventLog, Decision, KGNode/KGEdge (Observation/Hypothesis/Belief/Decision record types), Hypothesis, Experiment, DigitalTwin, JournalEntry, MemoryGovernanceLog
- `src/confidence.ts` — `calculateConfidence()` implementing `Confidence = w1·SignalReliability + w2·HistoricalAccuracy + w3·CausalMaturityScore`
- `src/decisionStateMachine.ts` — the Decision state machine (`Proposed → Presented → Accepted/Rejected/Ignored → OutcomeRecorded`, with `Revised` looping back to `Presented`)
- `src/recalc.ts` — the formal `recalc()`, replacing the flat "+1% per accepted item" heuristic in the `today_cockpit` HTML prototypes with real confidence-weighted forecast and timeline ordering
- `tests/` — unit tests (vitest) for all of the above

## Usage

```bash
npm install
npm run typecheck
npm test
```

## Persistence layer (PR #2)

- `src/persistence/SignalStoreRepository.ts` / `EventLogRepository.ts` — storage-agnostic interfaces. Every method returns a `Promise`, and `EventLogRepository` has no update or delete method at all, so the append-only guarantee is enforced by the type signature, not just convention.
- `src/persistence/InMemorySignalStoreRepository.ts` / `InMemoryEventLogRepository.ts` — the initial backend. A future `PostgresSignalStoreRepository` / `PostgresEventLogRepository` implements the same interfaces; no call site elsewhere in the codebase needs to change.
- `src/persistence/clone.ts` — every entry is deep-cloned (`structuredClone`) at both the write boundary (`append`/`upsert`) and the read boundary (`getAll`/`get`/`findByDecisionId`). Without this, callers could mutate an object they passed in or got back and silently rewrite "immutable" history — the append-only guarantee has to hold for real, not just be the absence of an `update()` method.
- `append()` on `EventLogRepository` throws `DuplicateEventLogEntryError` for a repeated `id`, mirroring the primary-key constraint any real database-backed implementation will also enforce.
- `tests/persistence/*.contract.ts` — a reusable behavioral test suite per interface (`runSignalStoreRepositoryContractTests`, `runEventLogRepositoryContractTests`), including mutation-after-write and mutation-after-read cases and the duplicate-id case. Any new implementation's test file just imports the contract and calls it with its own factory — if it passes, the implementation is a verified drop-in replacement.
- Recording an outcome after the fact means **appending** a new `EventLogEntry` for the same `decisionId`, not mutating the original — `findByDecisionId` reconstructs the full history in insertion order. This mirrors the immutable-history guarantee already enforced by the Decision state machine (`OutcomeRecorded` is terminal, `supersedesDecisionId` links a new decision back to an old one).

## Application service (PR #3)

- `src/application/DecisionApplicationService.ts` — the **only** entry point that is allowed to call `SignalStoreRepository`, `EventLogRepository`, or `recalc()`. Nothing else in the codebase (and, later, the API layer) should reach past this class into the repositories or domain functions directly.
- `recalculateDay()` always runs in this fixed order: read the current signal store → upsert the incoming signal delta → read the effective signal store back from the repository → call `recalc()` **against that persisted effective store** → append one `EventLogEntry` per accepted decision. `recalc()` is deliberately called with `currentSignalStore: effectiveSignalStore` and an empty delta, never with the raw pre-persistence values — a real (e.g. Postgres) repository may normalize, clamp, round, or otherwise transform values on write, so recalc() and the Event Log snapshot must reflect what was actually saved, not what was asked to be saved. Nothing is written to the Event Log until `recalc()` has succeeded.
- `src/application/types.ts` — `RecalculateDayCommand` / `RecalculateDayResult` (the only shapes a future API/UI layer needs to know about), plus the injectable `IdGenerator` and `Clock` dependencies (with `RandomIdGenerator` / `SystemClock` as the real-usage defaults) that keep event IDs and timestamps out of the service's own hands so tests can be fully deterministic.
- `src/application/errors.ts` — `ApplicationError` and its subclasses (`SignalPersistenceError`, `EventLogPersistenceError`, `RecalcExecutionError`) so callers outside this package only ever need to handle one error hierarchy, never repository- or recalc()-specific failures directly.
- The service never returns repository internals: signal stores, forecasts, and ID lists returned from `recalculateDay()` are freshly built values, so mutating a result never mutates stored state.
- **Not atomic (v1):** the per-decision `EventLogEntry` appends happen in a loop, one repository call per decision. If an append fails partway through, the entries already appended remain persisted — there is no rollback. Callers must not assume `recalculateDay()` is all-or-nothing. True atomicity needs a real transaction boundary and is deferred to the PostgreSQL adapter PR.

## Knowledge Graph (PR #4)

- `src/knowledge-graph/KnowledgeGraphRepository.ts` — storage-agnostic contract for `KGNode`/`KGEdge`: `addNode`, `getNode`, `getNodesByDomain`, `addEdge`, `getEdge`, `findEdgesFrom`, `findEdgesTo`, `findEdgesBetween`, `updateEdgeMaturity`, `getMaturityHistory`. Node and edge IDs must be unique; an edge cannot reference a `fromNodeId`/`toNodeId` that was never added via `addNode()`; `confidence` must be a finite number in `[0, 1]`; `evidenceCount` must be a safe (non-fractional) integer `>= 0`; a self-edge (`fromNodeId === toNodeId`) is rejected unless the caller explicitly passes `{ allowSelfEdge: true }`.
- `src/knowledge-graph/InMemoryKnowledgeGraphRepository.ts` — the initial backend, deep-cloning (via `../persistence/clone`) at every read and write boundary, exactly like the Signal Store / Event Log repositories from PR #2. IDs and timestamps are never generated inside the repository — callers supply fully-formed values (see `KnowledgeGraphService` below), including a fully-formed `transition` object (`recordId` + `timestamp` + optional `reason`/`overrideMaturityTransition`) for `updateEdgeMaturity()`, so repository behavior stays deterministic and testable without faking the system clock or ID generation.
- **Numeric validation** rejects `NaN` and `+/-Infinity` outright (`confidence < 0 || confidence > 1` alone would silently admit `NaN`, since every comparison against `NaN` is `false`): `assertValidConfidence` requires `Number.isFinite(value)`, and `assertValidEvidenceCount` requires `Number.isSafeInteger(value)` so fractional evidence counts are rejected too. Applied identically in `addEdge()` and `updateEdgeMaturity()`.
- `src/knowledge-graph/CausalMaturityPolicy.ts` — the only place causal maturity transition legality is decided (`correlated → suspected_causal → experimentally_supported → stable_causal`). A single natural step forward is always allowed. Skipping more than one step requires `overrideMaturityTransition: true` **and** a `reason`. Any downgrade (moving to a lower maturity) requires a `reason` — there is no silent downgrade path.
- **Maturity transition history:** every successful `updateEdgeMaturity()` call — including a same-state ("no_change") reinforcement — appends one `MaturityTransitionRecord` (`id`, `edgeId`, `from`, `to`, `kind`, `previousConfidence`/`nextConfidence`, `previousEvidenceCount`/`nextEvidenceCount`, `reason`, `overrideUsed`, `timestamp`) to an append-only, per-edge, deep-cloned history, mirroring the `EventLogRepository` pattern from PR #2: no update or delete method exists for these records. A failed validation (invalid confidence/evidenceCount, a disallowed maturity transition, or a duplicate `recordId`) writes nothing — neither the edge nor the history changes. `getMaturityHistory(edgeId)` returns the full trail in insertion order (an empty array for an edge with no history yet, or for an unknown edge id — it never throws). Previously, transition legality was validated but the outcome was never persisted anywhere, so there was no way to audit *why* an edge's maturity had changed; this closes that gap.
- **`MaturityTransitionRecord.id` uniqueness:** `updateEdgeMaturity()` rejects a `transition.recordId` that already identifies a record on *any* edge — not just the edge currently being updated — via `DuplicateMaturityTransitionRecordError`, checked before either the edge or the history is written. This mirrors `EventLogRepository`'s `DuplicateEventLogEntryError` guarantee from PR #2 and anticipates the `kg_maturity_history` table's primary key once a real database backend exists. (Flagged during PR #5 review as a gap in the PR #4 in-memory implementation; fixed here rather than deferred, since it was a small, self-contained change.)
- `src/knowledge-graph/KnowledgeGraphService.ts` — thin orchestration layer with injected `IdGenerator`/`Clock` (reusing the same interfaces from `src/application/types.ts`), so it's the only place that constructs `KGNode`/`KGEdge` IDs and timestamps, including the `recordId` for each maturity-transition record. Nothing outside this service should call `KnowledgeGraphRepository` directly. `getMaturityHistory()` is exposed as a thin passthrough so callers never need to reach past the service to read the audit trail.
- `tests/knowledge-graph/knowledgeGraphRepository.contract.ts` — reusable behavioral test suite (`runKnowledgeGraphRepositoryContractTests`), covering duplicate IDs, missing node references, invalid confidence/evidence (including `NaN`/`Infinity`/`-Infinity`/fractional evidenceCount), the self-edge rule, every maturity-transition case (natural step, rejected skip, allowed override-with-reason, rejected silent downgrade, allowed downgrade-with-reason), the full maturity-history audit trail (reason persisted on downgrade, `overrideUsed: true` on override, `reason: null` on a natural advance, a same-state reinforcement recording an event, stable insertion order across multiple updates, mutation-safety of returned records, and "failed validation writes nothing"), the two `DuplicateMaturityTransitionRecordError` cases (same edge, and cross-edge global uniqueness), defensive cloning, and insertion/query order. Any future `PostgresKnowledgeGraphRepository` test file just imports and calls this contract with its own factory.

## Learning Engine (PR #5)

- `src/learning/HypothesisRepository.ts` / `InMemoryHypothesisRepository.ts` — storage-agnostic contract and in-memory backend for `Hypothesis` records, mirroring every other repository in this codebase: `add`, `get`, `getByRelatedEdgeId`, `updateStatus`. Deep-cloned at every read/write boundary; `confidence`/`evidenceCount` validated with the same `Number.isFinite()`/`Number.isSafeInteger()` rules established in PR #4.
- `src/learning/HypothesisStateMachine.ts` — the only place a Hypothesis status transition is decided. Exactly three lifecycle paths are allowed: `forming → testing → confirmed`, `forming → testing → rejected`, and `forming → unknown_competing`. `confirmed`, `rejected`, and `unknown_competing` are terminal.
- `src/learning/ExperimentRepository.ts` / `InMemoryExperimentRepository.ts` — same pattern for `Experiment` records: `add`, `get`, `findByHypothesisId`, `updateStatus`. `add()` enforces the full guardrail field list (below); `updateStatus()` enforces both the structural lifecycle and the consent guardrail, and refuses any update once an experiment has reached a final status (`ExperimentImmutableError` — a completed experiment is immutable).
- `src/learning/ExperimentStateMachine.ts` — the purely structural lifecycle graph, the same for every experiment regardless of category: `proposed → awaiting_consent → baseline → running → washout → evaluated → confirmed / rejected / inconclusive`, with `aborted` reachable from any non-final status. `proposed → baseline` is also structurally valid — it's `ExperimentPolicy`'s job to block it for regulated categories.
- `src/learning/ExperimentPolicy.ts` — everything that isn't purely structural: the guardrail field checklist every experiment needs (`hypothesisId`, `intervention`, `singleVariable`, `durationDays`, `baselinePeriodDays`, `successMetric`, `stopRule`, `washoutPeriodDays`, `category`), the consent gate (`health`/`financial` experiments can never skip `awaiting_consent`, and leaving `awaiting_consent` for `baseline` always requires `consentGiven: true`, for every category), and the proof rules: a single confirmed experiment can promote an edge to at most `experimentally_supported`; `stable_causal` requires a documented minimum of confirmed experiments and elapsed days, consistent results, and no unresolved competing hypothesis (`qualifiesForStableCausal`).
- `src/learning/EvidenceEvaluator.ts` — deterministic mapping from a run's evidence (`effectObserved`, `metricMet`) to an outcome: no effect observed → `rejected`; effect observed and the pre-declared success metric met → `confirmed`; effect observed but metric not met → `inconclusive` (insufficient).
- `src/learning/HypothesisService.ts` / `ExperimentService.ts` — the orchestration boundary for this module, with injected `IdGenerator`/`Clock` (reusing `src/application/types.ts`). `ExperimentService.evaluate()` is the one place a confirmed experiment's result is connected back to its Hypothesis (moves it to `confirmed`) and to the Knowledge Graph edge (`relatedEdgeId`): it aggregates every confirmed experiment across every hypothesis tied to that edge to decide the resulting maturity, and calls `KnowledgeGraphService.reinforceEdge()` with `overrideMaturityTransition: true` only when the jump is more than one step (e.g. `correlated → experimentally_supported` on a first confirmed experiment) — never to reach `stable_causal` in a single step from below `experimentally_supported`, so an edge can never go from `correlated` straight to `stable_causal` no matter how strong one experiment's result is.
- `src/knowledge-graph/KnowledgeGraphService.ts` gained a `getEdge()` read passthrough in this PR, so `ExperimentService` can read an edge's current maturity/confidence before reinforcing it without reaching past `KnowledgeGraphService` into `KnowledgeGraphRepository` directly.
- `src/types.ts`'s `Experiment` gained a `consentGiven: boolean` field (previously only `requiresExplicitConsent` existed) — the explicit record of whether consent was actually granted, as opposed to whether it's required.
- `tests/learning/hypothesisRepository.contract.ts` / `experimentRepository.contract.ts` — reusable behavioral test suites, same pattern as `knowledgeGraphRepository.contract.ts`. Plus dedicated unit tests for both state machines, `ExperimentPolicy`'s guardrails/consent/proof rules, `EvidenceEvaluator`, and both services (including an end-to-end `ExperimentService` test proving an edge reaches `stable_causal` only after enough confirmed experiments/days accumulate, and stays capped at `experimentally_supported` while an unresolved competing hypothesis exists).

## Digital Twin + Memory Governance (PR #6)

- `src/types.ts` gained `DigitalTwinSnapshot` (`id`, `userId`, `derivedAt`, `stress`, `energyCurve`, `decisionStyle`, `behaviorPatterns`, `knownPreferences`, `activeConstraints`, `sourceVersions`) and `MemoryRecord`/`MemoryGovernanceRecord` (`MemoryState`: `Missing`/`Learning`/`Knows`; `MemoryRegressionReason`: `evidence_decay`/`stale_data`/`contradiction`/`user_correction`/`user_forget`/`experiment_opt_out`/`source_disabled`/`unreliable_source`) — deliberately kept separate from the pre-existing, lighter `DigitalTwin`/`MemoryGovernanceLogEntry` types, which `recalc()` and the Application Service already depend on and which this PR does not touch.
- `src/twin/DigitalTwinRepository.ts` / `InMemoryDigitalTwinRepository.ts` — storage-agnostic contract and in-memory backend for the append-only `DigitalTwinSnapshot` history (`save`, `getById`, `getLatest`, `getHistory`), following every convention established since PR #2: `Promise`-returning methods, deep-cloning at every read/write boundary, `DuplicateDigitalTwinSnapshotError` on a repeated id.
- `src/twin/TwinDerivationPolicy.ts` — the only place a Digital Twin's fields are actually computed, as pure, deterministic functions: `deriveStress` (from `mood_score`/`sleep_quality`, `"unknown"` when either is missing — never silently defaulted to `"low"`), `deriveEnergyCurve` (a fixed set of hours, each with `expectedEnergy`/`confidence` derived from `sleep_duration`, never the raw signal value itself), and `deriveDecisionStyle`/`deriveBehaviorPatterns`/`deriveKnownPreferences`/`deriveActiveConstraints` (from `Knows`, unblocked `MemoryRecord`s only — a blocked or not-yet-`Knows` memory is excluded even if the caller passes it in, so "blocked memory never enters the Digital Twin" holds regardless of what upstream code does).
- `src/twin/DigitalTwinService.ts` — thin orchestration layer with injected `IdGenerator`/`Clock`; the only place that constructs a snapshot's `id`/`derivedAt` and the only caller of `DigitalTwinRepository`. `deriveAndPersist()` never stores a raw `Signal` or `SignalStoreEntry` — every persisted field passes through `TwinDerivationPolicy` first.
- `src/memory/MemoryStateMachine.ts` — the structural lifecycle `Missing -> Learning -> Knows`, with regression `Knows -> Learning -> Missing`, mirroring the KG causal-maturity / Learning Engine state-machine pattern. Two explicit, narrowly-scoped overrides exist, each requiring the caller to also record a `reason`: `forceCollapse` (`Knows` straight to `Missing`, reserved for `MemoryDecayPolicy`'s `"stale_data"` case) and `userCorrection` (any state straight to `Knows`, reserved for `MemoryGovernanceService.correct()` — a direct user statement doesn't have to earn its way through `Learning` the way accumulated system inference does).
- `src/memory/MemoryDecayPolicy.ts` — deterministic, pure `evaluateDecay(memory, now)`: no regression before `DECAY_THRESHOLD_DAYS` (30) since `lastReinforcedAt`; one-step regression with reason `"evidence_decay"` after that; a forced collapse straight to `Missing` with reason `"stale_data"` after `STALE_THRESHOLD_DAYS` (90). Never reads the system clock itself — `now` is always caller-supplied.
- `src/memory/MemoryRepository.ts` / `InMemoryMemoryRepository.ts` — same atomic state-plus-audit-log pattern as `KnowledgeGraphRepository.updateEdgeMaturity()`: `updateState()` validates confidence/evidenceCount/transition legality, then writes the updated `MemoryRecord` and appends exactly one `MemoryGovernanceRecord` to an append-only, per-memory, deep-cloned log in the same call. `MemoryGovernanceRecord.id` uniqueness is enforced **globally**, across every memory's log, via `DuplicateMemoryGovernanceRecordError` — the same discipline just retrofitted onto `KnowledgeGraphRepository.MaturityTransitionRecord.id` earlier in this PR cycle, built in here from the start instead of deferred.
- `src/memory/MemoryGovernanceService.ts` — the only orchestration boundary allowed to call `MemoryRepository.add()`/`updateState()`: `createMemory`, `reinforce` (one promotion step per call — evidence has to accumulate to reach `Knows`, no shortcut), `correct` (user-authored, `confidence: 1`, uses the `userCorrection` override), `forget` (resets to `Missing` **and** sets `blocked: true`, so a forgotten fact stays excluded from every future Digital Twin even if the system re-learns it later), `blockInference`/`unblockInference` (toggle `blocked` without touching state or value), `applyDecay` (a no-op — no write, no governance record — when nothing is due), `applyContradiction`, `optOutExperiment`, `demoteForSourceIssue`.
- `src/memory/MemoryMapService.ts` — the read-only counterpart: `getMemoryMap` (everything, for "what does the system know about me"), `getKnownMemories` (`Knows` and not blocked — what `DigitalTwinService` should prefer as its memory input), `getGovernanceLog`. Nothing outside these two services should call `MemoryRepository` directly.
- `tests/twin/digitalTwinRepository.contract.ts` / `tests/memory/memoryRepository.contract.ts` — reusable behavioral test suites, same pattern as every other `*.contract.ts` file in this codebase. Plus dedicated unit tests for `TwinDerivationPolicy` (including an explicit no-raw-signal-leakage assertion against a marker value that must never appear in a persisted snapshot), `MemoryStateMachine`, `MemoryDecayPolicy`, `DigitalTwinService` (deterministic derivation across independent service instances, blocked-memory exclusion, cloning safety), and `MemoryGovernanceService` (the full `Missing -> Learning -> Knows` promotion path, correction, forget, block/unblock, decay, stale-data force-collapse, contradiction, cloning safety).

## Counterfactual Engine (PR #7)

- `src/counterfactual/Scenario.ts` — `buildScenarios(candidateDecisions)` builds one `Scenario` per candidate `Decision`, in input order. v1 evaluates exactly one decision per scenario (`decisionIds` always has length 1) — `candidateDecisions` are treated as mutually exclusive options for the same decision point (e.g. different times/actions for `gym_time`). `decisionIds` is kept as an array so a future version can evaluate combinations of decisions accepted together without changing the shape.
- `src/counterfactual/ScenarioEvaluator.ts` — `evaluateScenario()` is a pure, deterministic function of a `Scenario` and a `ScenarioEvaluationContext` (twin, signals, a `KnowledgeGraphSnapshot`, historical accuracy, baseline forecast). It never reads the clock, never generates an ID, and never mutates its inputs. `KnowledgeGraphSnapshot` is a plain, pre-computed view of the relevant Knowledge Graph edges (`edgesByDecisionType`) — the caller (the future `TodayDecisionApplicationService`, PR #8) builds it from `KnowledgeGraphRepository`, so this engine never depends on the live repository and stays trivially deterministic. A decision type's causal-maturity contribution is discounted by the strongest matching edge's own `confidence`, so a low-confidence relation can never act as a strong reason on its own. Each `ScenarioResult`'s `contributors` are normalized to sum to 1 (or 0 when every source is empty), so their relative weight is directly inspectable.
- `src/counterfactual/UncertaintyPolicy.ts` — `evaluateScoreUncertainty()` compares the top two ranked scenario scores. A gap under `NEAR_TIE_SCORE_THRESHOLD` (0.03) is reported as `{ isUncertain: true, reason: "near_tie", margin }` instead of picking a confident winner — a near-tie is treated as a real epistemic state, not rounding noise.
- `src/counterfactual/ExplainAlternatives.ts` — `buildExplanation()` derives every `selectedBecause`/`rejectedBecause` string directly from a `ScenarioResult`'s own `contributors` (its strongest contributors for the winner, its weakest plus the score gap for each alternative) — never a separately hand-written string, so the explanation can never drift from the numbers that actually drove the outcome.
- `src/counterfactual/CounterfactualEngine.ts` — `runCounterfactualEngine()` is the single entry point: builds and ranks scenarios, decides uncertainty, and assembles the explanation. Two cases are handled as clear, well-formed results rather than exceptions: an empty `candidateDecisions` list (`selectedScenario: null`, `uncertainty.reason: "no_candidates"`) and an empty `signals` store (`uncertainty.reason: "missing_signals"` — scenarios are still computed and returned as `alternatives` so a caller has something to show, but no confident winner is selected). The whole engine is a pure function: identical input always produces identical output, and no input object is ever mutated.
- `src/counterfactual/errors.ts` — `CounterfactualError` / `CounterfactualComputationError`, reserved for genuine internal-consistency failures. The expected degenerate cases above are not errors — see `CounterfactualEngine.ts`.
- `tests/counterfactual/` — `counterfactualEngine.test.ts` covers determinism, no-mutation, empty candidates, missing signals, a low-confidence-graph comparison, tie/near-tie/wide-gap uncertainty, bounded probabilities, contributor normalization, and explanation consistency, exactly matching the required test list. `scenarioEvaluator.test.ts`, `uncertaintyPolicy.test.ts`, and `explainAlternatives.test.ts` cover each pure function in isolation.

## Decision Orchestration v2 (PR #8)

- `src/application/TodayDecisionApplicationService.ts` — a new orchestration service that runs the complete Today decision path in one call: Signals -> Signal Store -> Digital Twin -> Knowledge Graph -> Hypotheses/Experiments -> Counterfactual Engine -> Decision -> `recalc()` -> Event Log -> Memory Updates. It does **not** replace `DecisionApplicationService` (the v1 service, still used on its own for pure forecast/timeline recalculation from already-accepted decisions) — both exist side by side, an explicit decision documented on both classes rather than a silent swap.
- Write ordering is enforced end to end: no `EventLogEntry` is appended and no memory decay is applied unless Digital Twin derivation, the Knowledge Graph reads, and the Counterfactual Engine all succeed first; a `null` decision (empty candidates, or an uncertain outcome) writes nothing at all.
- `src/knowledge-graph/KnowledgeGraphService.ts` gained three read passthroughs — `getNodesByDomain`, `findEdgesFrom`, `findEdgesTo` — so this new orchestration can build a `KnowledgeGraphSnapshot` for the Counterfactual Engine without reaching past the service into `KnowledgeGraphRepository` directly, the same justification as the `getEdge()` passthrough added in PR #5.
- `src/types.ts`'s `UserAction` gained a `"proposed"` value: the system recording that it generated and presented a recommendation (with its context and alternative scenarios embedded in `recommendation`), with `outcome: "pending"`, before the user has responded at all. Once the user responds, a *separate* `"accepted"`/`"rejected"`/`"ignored"` entry is appended for the same `decisionId` — the original `"proposed"` entry is never mutated, matching the Event Log's append-only guarantee.
- The Counterfactual Engine selects *which* decision to propose from `candidateDecisions`; `recalc()` continues to move forecast/timeline off of `previouslyAcceptedDecisions` exactly as it did in v1 — the two concepts (today's candidate options vs. history already committed to) are kept distinct rather than conflated.
- Non-atomicity: the Event Log append and the per-memory decay loop are separate calls, same caveat as `DecisionApplicationService.recalculateDay()` — a real transaction boundary needs Postgres (PR #11).
- `tests/application/todayDecisionApplicationService.test.ts` — a 12-step end-to-end test (InMemory repositories) covering signal ingestion, Knowledge Graph edge reinforcement, hypothesis testing, decision selection, Event Log append-only history across two simulated days, and forecast movement once a decision is accepted.

## API Layer v1 (PR #9)

- `src/api/` — a small, dependency-light HTTP layer (only `zod` for validation and `supertest` for tests were added; no framework) exposing the Today Cockpit's application endpoints: `POST /api/signals`, `GET /api/signals/current`, `POST /api/today/recalculate`, `GET /api/today`, `POST /api/decisions/:id/respond`, `POST /api/decisions/:id/outcome`, `GET /api/decisions/:id/history`, `GET /api/memory`, `POST /api/memory/:id/correct`, `POST /api/memory/:id/forget`, `POST /api/memory/:id/block`, `GET /api/system/health`.
- `src/api/router.ts` — a minimal hand-rolled router (method + `/segment/:param` pattern matching) rather than adopting a framework, consistent with this repo's dependency-light approach so far; `src/api/server.ts` turns it into a plain Node request-listener function usable both with `http.createServer()` for real usage and directly with `supertest` in tests.
- `src/api/auth.ts` — an `AuthContext`/`AuthResolver` abstraction from the start: `MockHeaderAuthResolver` (v1) trusts an `x-user-id` header as-is and is explicitly documented as not real authentication; every route handler only depends on the `AuthResolver` interface, so PR #12's real session/token auth replaces it without touching a single route.
- `src/api/container.ts` — `AppContainer` builds and memoizes one full, independent bundle of repositories and services per `userId` (`UserServices`). This is how "every request bound to userId; no state sharing between users" holds in an in-memory, single-process API: isolation by construction, not by a runtime filter over shared storage — a request for another user's decision/memory id structurally can't be found rather than needing an explicit ownership check. PR #11 swaps the `InMemory*` repositories built here for Postgres-backed ones scoped by a `user_id` column without changing `AppContainer`'s public shape.
- `src/application/SignalIngestionService.ts` / `DecisionLifecycleService.ts` — two small new Application Services added so every route still only ever calls a service, never a repository directly: signal ingestion/reads outside of a full Today recalculation, and appending response/outcome `EventLogEntry` rows (`respond()`, `recordOutcome()`, `getHistory()`) while enforcing that an outcome can't be recorded before the user has responded at least once (`DecisionNotYetRespondedError`).
- `src/api/errors.ts` — `mapErrorToHttpResponse()` is the single place a thrown error becomes an HTTP status + structured JSON body (`{ error: { name, message, requestId, issues? } }`), never a stack trace: Zod validation failures -> 400, no `AuthContext` -> 401, `Unknown*` domain errors -> 404, `Duplicate*` domain errors -> 409, any other recognized domain error base class (`ApplicationError`, `DigitalTwinError`, `MemoryError`, `KnowledgeGraphError`, `LearningError`, `CounterfactualError`) -> 422, anything unrecognized -> 500 with a generic message.
- `tests/api/api.test.ts` — `supertest`-driven tests covering the health check, missing-auth 401s, malformed-body 400s, unknown-route 404s, a full signals -> today -> respond -> outcome -> history flow, the `DecisionNotYetRespondedError` 422 case, unknown-memory 404s, and a dedicated per-user isolation test proving one user's signals/decisions/memory are never visible to another user's requests.

## PostgreSQL Adapter v1 (PR #11)

- `migrations/001_init.sql` — the schema for a Postgres-backed `signal_store` table (one row per signal type, upserted) and an append-only `event_log` table. `event_log` has both a business `"timestamp"` column and a storage-only `seq SERIAL` column: two entries can legitimately share the same timestamp, so `seq` is what actually guarantees `findByDecisionId`/`getAll` reconstruct true insertion order, matching the in-memory implementation's array-push ordering exactly.
- `src/persistence/postgres/PostgresSignalStoreRepository.ts` and `PostgresEventLogRepository.ts` — Postgres implementations of the exact same `SignalStoreRepository`/`EventLogRepository` interfaces from PR #2, with no changes to either interface. Both were written specifically to fulfill the promise already sitting in this codebase's own doc comments ("a future PostgresSignalStoreRepository... implementing the same interface — no call site anywhere else in the codebase should need to change").
- `PostgresEventLogRepository` enforces the same duplicate-id rejection as the in-memory implementation, but via a real `UNIQUE` constraint (Postgres error code `23505`) instead of an array scan — `append()` catches that constraint violation and re-throws it as the same `DuplicateEventLogEntryError` either backend would throw, so callers can't tell which one they're talking to.
- `src/persistence/postgres/Queryable.ts` — both adapters depend on this narrow `{ query() }` interface rather than importing `pg.Pool` directly, so tests can swap in a fake without a real Postgres server.
- `tests/persistence/postgres/` — a **contract test suite**: the same behavioral test bodies (round-trip, overwrite, delete-is-noop, insertion-order, duplicate-id rejection, no-shared-reference-on-read) are run once against `InMemorySignalStoreRepository`/`InMemoryEventLogRepository` and once against `PostgresSignalStoreRepository`/`PostgresEventLogRepository`. The Postgres side runs against [pg-mem](https://github.com/oguimbal/pg-mem), an in-memory Postgres-wire-compatible engine, since no sandbox or CI runner here has a real Postgres server available — pg-mem executes the real SQL these adapters send (including `ON CONFLICT` upserts and constraint violations), so this is a genuine test of the adapters' SQL, not a mock of them. Production deployment targets real Postgres via the `pg` driver; pg-mem is a test-only substitute for the driver, not for the adapters.
- **Scope note**: this PR adds the Postgres adapters and proves them a drop-in replacement for the storage-agnostic interfaces; it does not yet wire `AppContainer` to use them instead of the in-memory repositories, and does not yet add multi-tenant `user_id` scoping to the Postgres tables. `AppContainer` currently achieves per-user isolation by giving each user their own in-memory repository instances; a single shared Postgres database needs an explicit `user_id` column and query scoping to get the same guarantee. That wiring is deferred to land together with PR #12 (real authentication), since that's the point at which "the authenticated user" becomes a concept enforced at the API boundary rather than a header taken on trust — scoping the database before that would just move the trust-boundary problem, not close it.

## Auth + Security Baseline (PR #12)

- `src/auth/` — a new bounded context: `User`/`Session` types, `UserRepository`/`SessionRepository` interfaces with `InMemory*` implementations (same storage-agnostic pattern as every other repository — see PR #11), password hashing (`node:crypto` `scrypt`, per-user random salt, timing-safe comparison, no new dependency), `LoginRateLimiter` (fixed-window, keyed by normalized email, injectable `Clock`), and `AuthService` (`register()`, `login()`, `logout()`, `resolveSession()`) — the only place account creation, login, and session verification happen.
- `src/api/auth.ts` — `SessionTokenAuthResolver` reads `Authorization: Bearer <token>` and asks `AuthService.resolveSession()` to look it up, replacing `MockHeaderAuthResolver` as `createApp()`'s default. This is exactly the swap PR #9's own doc comment on `AuthResolver` promised: no route handler changed, only which `AuthResolver` implementation `createApp()` constructs. `MockHeaderAuthResolver` is still exported for local scripting but is no longer wired by default.
- `src/api/routes/auth.ts` — `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` (all `public: true`, since there is no authenticated user yet when they run). Built by a factory (`createAuthRoutes(authService)`) rather than static `Route` exports, since they close over a shared `AuthService` instance instead of receiving the per-user `AppContainer` every other route gets.
- Password policy (`src/api/schemas.ts`'s `passwordSchema`): minimum 10 characters, at least one letter and one digit — enforced via Zod, so weak passwords surface as an ordinary `ValidationError` 400 with no separate error class needed.
- `AuthService.login()` runs a real `scrypt` verification against a fixed dummy hash even when the email isn't registered, so "no such account" and "wrong password" take the same amount of time — a client can't time responses to enumerate which emails have accounts. Failed logins never distinguish the two in their error message either (`InvalidCredentialsError`).
- New error mappings in `src/api/errors.ts`: `InvalidCredentialsError` -> 401, `TooManyLoginAttemptsError` -> 429 (rate limit tripped), `DuplicateEmailError` -> 409 (via the existing generic `Duplicate*`-prefix convention, no new mapping code needed).
- `tests/auth/` — unit tests for `AuthService` (register/login/logout/session-expiry/rate-limit-reset-on-success), `LoginRateLimiter` (window expiry, per-key isolation), `passwordHashing` (round-trip, wrong password, random salting, malformed-hash safety), and both in-memory repositories (defensive-clone isolation, matching every other in-memory repository's tests). `tests/api/api.test.ts` was updated to register/log in real users instead of trusting an `x-user-id` header, plus new coverage for duplicate registration, wrong password, weak password, and logout revocation.
- **Scope note**: this PR does not add authorization rules beyond authentication (no roles/permissions — `ForbiddenError` remains unused, as documented since PR #9), does not add refresh tokens (sessions are single opaque tokens with a fixed 7-day TTL, revocable via logout), and does not yet move `UserRepository`/`SessionRepository` onto Postgres (they follow PR #11's pattern and are drop-in replaceable the same way, but that migration isn't part of this PR).

## Google Calendar Integration (PR #13)

- `src/calendar/` — a new bounded context, following the exact PR #11 precedent (real implementation behind a narrow interface, deterministic fake substituted in tests, never a mock of the code under test): `CalendarConnection`/`CalendarEvent` types, `CalendarConnectionRepository` interface with `InMemoryCalendarConnectionRepository`, `CalendarProvider` interface (no write method exists on it anywhere — read-only is enforced structurally, matching `EventLogRepository`'s append-only pattern), `GoogleCalendarProvider` (real implementation via native `fetch` against the Google Calendar v3 events endpoint and the OAuth token-refresh endpoint, no new dependency), `FakeCalendarProvider` (deterministic test/default substitute), and `CalendarSignalService` (the sole Application Service for this context).
- **Data minimization**: `CalendarSignalService.sync()` reads a 24-hour window of upcoming events and derives exactly one signal — `meeting_count` (an integer) — then discards the raw events. Titles, attendees, locations, and every other field from the provider response are never persisted anywhere. This is verified directly in `tests/calendar/calendarSignalService.test.ts` ("never persists raw event content").
- **Token handling**: `CalendarConnection.accessToken`/`refreshToken` are stored in-memory only in v1. `CalendarConnectionRepository`'s doc comment flags that any future Postgres-backed implementation (following the PR #11 pattern) **must** encrypt these columns at rest before it is used in production — this is an explicit, tracked gap, not a silent one. API responses never echo the raw tokens back: routes always return `PublicCalendarConnection` (via `toPublicCalendarConnection()`), which omits both fields, mirroring the auth module's `PublicUser`/`toPublicUser` pattern for `passwordHash`.
- **v1 OAuth scope**: this service does not broker or initiate Google's OAuth consent flow. The client is expected to complete that flow itself (e.g. in the frontend) and hand the resulting access/refresh token pair to `POST /api/calendar/connect`. Server-side OAuth exchange (authorization-code flow, client-secret-protected token exchange) is explicitly out of scope for v1 and is a documented limitation, not an unstated gap.
- `src/api/routes/calendar.ts` — `POST /api/calendar/connect`, `GET /api/calendar/connection`, `DELETE /api/calendar/connection`, `POST /api/calendar/sync`, all protected (require a bearer session token) and scoped to the authenticated user via `container.forUser(auth.userId)`, same as every other route since PR #12.
- `src/api/container.ts` — `AppContainer` now takes an optional third constructor argument, a single `CalendarProvider` shared across every user's container (unlike the per-user repositories, it holds no per-user state — it only knows how to call the API given whatever connection it's passed). Defaults to `FakeCalendarProvider`; real deployment should construct `AppContainer` with a `GoogleCalendarProvider` built from real OAuth client credentials.
- New error mapping in `src/api/errors.ts`: `CalendarProviderError` -> 502 (upstream Google API failure), joining the existing `Unknown*` -> 404 / `Duplicate*` -> 409 conventions (`UnknownCalendarConnectionError` already 404s via the existing prefix rule, no new mapping code needed for it).
- `tests/calendar/calendarSignalService.test.ts` — unit tests for connect/disconnect/getConnection, sync's 24h window filtering, the data-minimization guarantee, and access-token refresh (both the refreshed-and-persisted case and the no-refresh-available case). `tests/api/calendar.test.ts` — API-level tests for auth-required, connect/get/disconnect/sync, invalid-body 400, unknown-connection 404, token redaction in responses, and per-user isolation.
- **Scope note**: no calendar write operations exist or are planned for v1 (read-only per Hadeel's explicit instruction). `CalendarConnectionRepository` is not yet Postgres-backed (same pending migration as `UserRepository`/`SessionRepository` from PR #12) — encryption-at-rest for tokens must land as part of that migration before any production use with real user data.

## Gmail Integration (PR #14)

- `src/gmail/` — a new bounded context, structurally identical in shape to PR #13's Calendar integration: `GmailConnection` type, `GmailConnectionRepository` interface with `InMemoryGmailConnectionRepository`, `GmailProvider` interface, `GoogleGmailProvider` (real implementation via native `fetch`, no new dependency), `FakeGmailProvider` (deterministic test/default substitute), and `GmailSignalService` (the sole Application Service for this context).
- **Stricter data minimization than Calendar**: `GmailProvider` exposes only `countUnread()` — there is no method on the interface that could ever return a message subject, sender, or body, even in principle. `GoogleGmailProvider` calls Gmail's `users.messages.list` with `q=is:unread in:inbox` and `maxResults=1`, reading only the `resultSizeEstimate` field of the response; it never requests message metadata or content. This is one step stricter than the Calendar integration, which at least receives event titles before discarding them.
- The derived signal is `custom:unread_email_count` — not one of the pre-existing `KnownSignalType` values in `src/types.ts`. Rather than widening that union for a single integration, this uses the `custom:${string}` extension point the type was explicitly designed to support.
- **Token handling**: identical model to Calendar (PR #13) — `GmailConnection.accessToken`/`refreshToken` are in-memory only in v1, and any future Postgres-backed implementation must encrypt these columns at rest before production use (flagged in the repository interface's doc comment). API responses always return `PublicGmailConnection` (via `toPublicGmailConnection()`), never the raw tokens.
- **v1 OAuth scope**: same as Calendar — the client completes Google's OAuth consent flow itself and hands the resulting token pair to `POST /api/gmail/connect`. This service never brokers or initiates the OAuth exchange.
- `src/api/routes/gmail.ts` — `POST /api/gmail/connect`, `GET /api/gmail/connection`, `DELETE /api/gmail/connection`, `POST /api/gmail/sync`, all protected and scoped to the authenticated user via `container.forUser(auth.userId)`.
- `src/api/container.ts` — `AppContainer` gains an optional fourth constructor argument, a single `GmailProvider` shared across every user's container, same rationale as `calendarProvider` (PR #13). Defaults to `FakeGmailProvider`.
- New error mapping in `src/api/errors.ts`: `GmailProviderError` -> 502, joining `CalendarProviderError` -> 502 from PR #13.
- `tests/gmail/gmailSignalService.test.ts` — unit tests for connect/disconnect/getConnection, the derived-signal persistence, the "nothing beyond the count is ever stored" guarantee, and access-token refresh (both branches). `tests/api/gmail.test.ts` — API-level tests mirroring the Calendar route test suite (auth-required, connect/get/disconnect/sync, invalid-body 400, unknown-connection 404, token redaction, per-user isolation).
- **Scope note**: no Gmail write operations exist or are planned for v1 (read-only, and the interface makes it structurally impossible to add a "send" or "modify" method without changing `GmailProvider` itself). `GmailConnectionRepository` is not yet Postgres-backed — same pending migration as `CalendarConnectionRepository`, `UserRepository`, and `SessionRepository`.

## Observability & Reliability (PR #15)

- `src/observability/` — a new cross-cutting infrastructure module, injectable the same way `Clock`/`IdGenerator` are (`src/application/types.ts`): `Logger` (`ConsoleLogger` for real usage, `NullLogger` as the default so tests stay silent, `InMemoryLogger` as the capturing test double), `MetricsCollector` (`InMemoryMetricsCollector`: request counts, error rate, p50/p95/max latency, per-status breakdown), `withRetry` (exponential-backoff retry for async operations), and `CircuitBreaker` (closed/open/half-open, fails fast once a dependency is sustained-down instead of letting every request separately time out).
- `src/api/server.ts` — every request now flows through one `finish()` seam that records a `MetricsCollector` sample and a structured `Logger` line (method, path, status, durationMs, requestId — never request/response bodies or auth headers) exactly once, regardless of which code path produced the response. No route handler needed to change to get this; it wraps `createApp()`'s dispatch loop only. `CreateAppOptions` gained optional `logger`/`metricsCollector`, both defaulted so no existing test needed to change except the health-check body assertion (see below).
- `GET /api/system/health` now also returns `uptimeSeconds` (still public, still reveals no signal/user data — just process liveness). `GET /api/system/metrics` (new, public, read-only) exposes the current `MetricsCollector` snapshot for dashboards/alerting — aggregate operational data only, no per-user content.
- **Reliability for the PR #13/#14 external integrations**: `GoogleCalendarProvider` and `GoogleGmailProvider` now wrap every Google API call in `withRetry` (3 attempts, exponential backoff) inside a `CircuitBreaker` (opens after 5 consecutive failures, 30s cooldown before a half-open trial). A `CircuitOpenError` maps to the same 502 as `CalendarProviderError`/`GmailProviderError` in `src/api/errors.ts`. This means a single transient network blip against Google no longer surfaces as a user-facing failure, and a sustained Google outage fails fast instead of every request from every user separately retrying and timing out.
- **v1 scope note**: `withRetry` does not distinguish retryable from non-retryable errors — every failure is retried up to `maxAttempts` (a deliberate v1 simplification; a 4xx from Google, e.g. an invalid token, is retried the same as a network blip before ultimately surfacing as a `CalendarProviderError`/`GmailProviderError`). Metrics and logs are in-memory/stdout only — there is no external metrics backend (Prometheus, Datadog, etc.) or log aggregation wired up; `MetricsCollector`/`Logger` are the injectable seams a future PR would point at one.
- `tests/observability/` — unit tests for `InMemoryLogger`, `InMemoryMetricsCollector` (zero-state, status bucketing, 5xx-only error rate, percentiles), `withRetry` (immediate success, eventual success, exhausted retries, exponential backoff timing, `maxAttempts: 1` short-circuit), and `CircuitBreaker` (closed happy path, opens at threshold, fails fast while open without calling the operation, half-open recovery, re-opens on a failed trial, failure-count reset on success). `tests/calendar/googleCalendarProvider.test.ts` and `tests/gmail/googleGmailProvider.test.ts` — verify the real providers actually retry transient `fetch` failures and that an open circuit breaker prevents any further `fetch` calls. `tests/api/metrics.test.ts` — `GET /api/system/metrics` shape, that requests are recorded against an injected collector, and that requests are logged through an injected logger.

## MVP Hardening

The final pass before real personal use, requested after `release/mvp-rc1`'s review. Twelve changes, in the order implemented:

1. **PostgreSQL is now the default storage backend.** `src/persistence/postgres/StorageBackend.ts` introduces `StorageBackend` (`InMemoryStorageBackend` / `PostgresStorageBackend`) and `defaultStorageBackend()`: if `DATABASE_URL` is set, every per-user repository (signal store, event log, digital twin, memory + governance log, knowledge graph nodes/edges/maturity history, hypotheses, calendar/gmail connections) is Postgres-backed and scoped by a `user_id` bound at construction time — the same isolation guarantee the in-memory design had (fresh instance per user), now enforced by a `WHERE user_id = $1` filter on a shared table instead of by separate JS objects. Without `DATABASE_URL`, the process falls back to in-memory storage and logs a loud warning — this fallback exists only for local development and the test suite (no test in this repo sets `DATABASE_URL`), never for a real deployment. `AppContainer`'s public shape did not change; only `buildUserServices()`'s repository construction did, exactly as PR #11's own doc comment anticipated.
2. **`UserRepository`/`SessionRepository` moved to Postgres.** `PostgresUserRepository`/`PostgresSessionRepository` follow the same interface both `InMemory*` versions already implemented. `createDefaultAuthService()` in `src/api/server.ts` picks Postgres when `DATABASE_URL` is set, in-memory otherwise — same fallback discipline as (1). Proven end-to-end (not just unit-tested) by `tests/persistence/postgres/restart.test.ts`, which boots a real embedded Postgres server, spawns the real `src/main.ts` entrypoint as a child process, registers a user and logs in over real HTTP, kills that process, spawns a brand-new one against the same database, and confirms the same session token still resolves and previously-written data is still there.
3. **Calendar/Gmail tokens are now encrypted at rest.** `src/security/tokenCipher.ts` — AES-256-GCM, random 96-bit IV per encryption, auth tag verified on decrypt (`TokenDecryptionError` on any tampering or wrong key). `PostgresCalendarConnectionRepository`/`PostgresGmailConnectionRepository` encrypt `accessToken`/`refreshToken` before every `INSERT`/`UPDATE` and decrypt only in-process on read — the `calendar_connections`/`gmail_connections` tables never contain plaintext tokens (verified directly in `tests/calendar/postgresCalendarConnectionRepository.test.ts` / the Gmail equivalent, which query the raw table and assert the stored value never contains the plaintext token).
4. **The encryption key is environment-only.** `TOKEN_ENCRYPTION_KEY` (a base64-encoded 32-byte key) is read from `process.env` at encrypt/decrypt time and is never hardcoded, logged, or committed — `tokenCipher.ts` throws `MissingEncryptionKeyError`/`InvalidEncryptionKeyError` rather than falling back to a default key if it's absent or malformed. See "Environment Variables" below for how to generate one.
5. **OAuth token exposure to the frontend is minimized.** `src/security/googleOAuth.ts` adds `GoogleTokenExchanger` (`GoogleOAuthTokenExchanger` for real usage, `FakeGoogleOAuthTokenExchanger` for tests/local dev) and two new routes, `POST /api/calendar/oauth/exchange` and `POST /api/gmail/oauth/exchange`: the frontend now only ever needs to hand the backend the short-lived, single-use authorization `code` from Google's OAuth redirect — the actual access/refresh token exchange happens server-to-server using this server's own `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, so the refresh token (the most sensitive, longest-lived credential) never transits through the browser or our API request body. `POST /api/calendar/connect` / `POST /api/gmail/connect` (the PR #13/#14 raw-token-pair routes) still exist for local dev, tests, and the mock-provider connect flow the frontend's "Connect (mock)" buttons use — but every real deployment should use the `/oauth/exchange` routes instead.
6. **A real Playwright E2E suite now exists** (new top-level `e2e/` package, sibling to `decision-engine/` and `frontend/`) covering, in one ordered journey: registration, a usable login session, the Today Cockpit rendering for an authenticated user, connecting Calendar via the mock provider, connecting Gmail via the mock provider, a real backend process restart (kill + respawn against the same Postgres database) with the session and both connections surviving it, and logout. `e2e/global-setup.ts` boots a real embedded Postgres server and the real `src/main.ts` entrypoint; `e2e/playwright.config.ts` boots the real Vite dev server for the frontend, proxying `/api` to the backend. **Building this suite surfaced a real, pre-existing integration gap**: the frontend (PR #10) predates real session auth (PR #12) and was still sending the old mock `x-user-id` header, which the real backend's default `SessionTokenAuthResolver` ignores entirely — meaning the deployed frontend could not authenticate against the real backend at all before this pass. Fixing this required adding the minimal UI that was missing: `AuthScreen` (register/login form), a logout button, `ConnectorsPanel` (Calendar/Gmail connect/disconnect), and switching `ApiClient` from the `x-user-id` header to `Authorization: Bearer <token>`. This is documented here rather than silently folded in because it's a bigger fix than "add tests" — it's what actually makes MVP RC1 usable end-to-end for the first time. A dedicated `E2E CI` workflow (`.github/workflows/e2e-ci.yml`) runs this suite on `ubuntu-latest` (which has Playwright's required system libraries preinstalled — this sandbox does not, and has no root/package-mirror access to install them; the suite is fully written, typechecked, and its non-browser orchestration — Postgres boot, backend boot, frontend boot — was verified locally, but the actual browser-driven assertions could only be verified via this PR's CI run, not locally).
7. **A dedicated test proves data and sessions survive a restart** — see (2) above (`tests/persistence/postgres/restart.test.ts`) and the E2E suite's restart step in (6). Both exercise a real OS process boundary, not just a fresh repository instance in the same test process.
8. **Migrations and a rollback strategy.** `migrations/002_hardening.sql` adds `user_id` scoping to the PR #11 tables (`signal_store`, `event_log`) and creates every new table this pass needs (`users`, `sessions`, `digital_twin_snapshots`, `memory_records`, `memory_governance_records`, `kg_nodes`, `kg_edges`, `kg_maturity_transitions`, `hypotheses`, `calendar_connections`, `gmail_connections`) — every statement is idempotent, matching `001_init.sql`'s style. `migrations/002_hardening_ROLLBACK.sql` is the explicit reverse of every statement, documented as destructive (drops tables) and intended only for reverting before any real data exists against the new schema. `src/persistence/postgres/pool.ts`'s `runMigrations()` now applies every file in `MIGRATION_FILES` in order; `src/main.ts` calls it once at startup when `container.storageMode === "postgres"`. See "Migrations & Rollback" below for the full decision tree.

See `Dockerfile` and `docs/DEPLOYMENT.md` for a single-container deployment recipe and the full environment variable list. ### Migrations & Rollback

- Migrations live in `migrations/*.sql`, applied in the order listed in `src/persistence/postgres/pool.ts`'s `MIGRATION_FILES` array — that array, not directory globbing, is the source of truth for ordering.
- Every statement in every migration file is idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, guarded `ALTER`s) — re-running `runMigrations()` against an already-migrated database is always safe.
- `src/main.ts` runs `runMigrations()` automatically at startup whenever the storage backend is Postgres. There is no separate "migrate" CLI step to remember.
- **Rollback decision tree**: if `release/mvp-rc1`'s changes need to be reverted before any real personal data has been written against the new schema, run `migrations/002_hardening_ROLLBACK.sql` directly against the database, then revert the corresponding commits on `main`/the deployed branch. If real data already exists, do **not** run the rollback SQL (it drops tables) — instead revert only the application code and leave the schema as-is (every new table the code no longer reads is simply unused, not harmful) until a proper data-preserving migration can be written.
- Any future schema change should follow the same pattern: a new numbered `NNN_description.sql` (idempotent, appended to `MIGRATION_FILES`) plus a matching `NNN_description_ROLLBACK.sql`.

### Security Review

| Item | Status |
|---|---|
| Rate limiting | `LoginRateLimiter` (PR #12) protects `/api/auth/login` specifically (5 attempts / 15 min per email). `RequestRateLimiter` (new) adds a global per-IP budget (300 requests / 60s by default) in front of every route, checked before routing in `src/api/server.ts`'s `handleRequest` — defense in depth beyond login. |
| Session expiration | Sessions have a fixed 7-day TTL (`AuthService`'s `DEFAULT_SESSION_TTL_MS`); `resolveSession()` checks `expiresAt` on every request and revokes (deletes) an expired session rather than just rejecting it, so it can never be "reactivated" by clock skew. |
| Token rotation | Calendar/Gmail access tokens are refreshed and re-persisted automatically when expired (`CalendarSignalService.ensureFreshToken()` / `GmailSignalService`'s equivalent), calling `GoogleCalendarProvider.refreshAccessToken()` / `GoogleGmailProvider`'s equivalent and writing the new token back before use. Session tokens are not rotated mid-session (a new one is simply issued on each login); there is no refresh-token concept for sessions themselves — logout is immediate revocation instead. |
| User isolation | Enforced at two layers now: (1) `AppContainer.forUser()` never shares a repository instance across users (unchanged since PR #9); (2) every Postgres repository is bound to a `user_id` at construction and filters every query by it, so a shared table cannot leak rows across tenants even if application code somehow requested the wrong container. Verified directly in the new Postgres repository tests (`tests/*/postgres*.test.ts`, "isolates ... by bound userId" cases). |
| Secret leakage in logs/API responses | Audited: `Logger`'s request-logging seam in `server.ts` only ever passes `{requestId, method, path, status, durationMs}` — never a body, header, or token. Every route returning a `User`/`CalendarConnection`/`GmailConnection` uses the corresponding `toPublicX()` redaction function (`passwordHash`/`accessToken`/`refreshToken` are never serialized). `tokenCipher.ts`'s stored ciphertext format contains no plaintext fragment of the original token. No `console.log`/`Logger` call anywhere in `src/` logs a request body, a token, or a password. |
| Not covered by this pass | No formal third-party security audit or penetration test. No confirmed CSRF protection layer (session tokens are bearer tokens in an `Authorization` header, not cookies, which structurally avoids classic CSRF — but this hasn't been explicitly reviewed as a CSRF mitigation). No trusted-proxy configuration for `RequestRateLimiter`'s IP detection (`req.socket.remoteAddress` is correct for a directly-exposed single process, but would show a reverse proxy's IP for every client if deployed behind one — documented here as a known limitation, not implemented, since no real deployment exists yet). |

The Today Cockpit UI (PR #10) is live against the API layer, backed by real authentication (PR #12) and, as of MVP Hardening, a real login/logout UI wired to it. PostgreSQL is now the **default** storage backend for every domain (signal store, event log, digital twin, memory, knowledge graph, hypotheses, calendar/gmail connections, users, sessions) whenever `DATABASE_URL` is set, with every table scoped by `user_id`; without it, the process falls back to in-memory storage for local dev/tests only. The Google Calendar (PR #13) and Gmail (PR #14) connectors are live, read-only, data-minimizing, encrypt tokens at rest, support a server-side OAuth code exchange that never exposes the refresh token to the browser, and retry/circuit-break transient failures (PR #15). Structured request logging, an operational metrics endpoint, and a global per-IP rate limit are live. A real Playwright E2E suite covers the full register → login → use → connect Calendar/Gmail (mock) → restart → logout journey, including a real process-restart proof and a basic accessibility check. `release/mvp-rc1` remains not merged, pending Hadeel's review of the MVP Hardening pass.

## Design notes from review

- `recalc()` takes both `currentSignalStore` (the full known state) and `signalStoreDelta` (what changed since the last pass), and merges them before computing confidence. Using the delta alone would zero out confidence during a quiet period with no fresh signals, even though the system's last-known state is still valid.
- `SignalType` is `KnownSignalType | \`custom:${string}\`` rather than `KnownSignalType | string` — the latter silently widens the whole union to `string` and defeats type-checking.
- `OutcomeRecorded` is a terminal state. A decision whose outcome has been logged is closed history and is never rewritten. If new signals change the recommendation afterward, a new `Decision` is created with `supersedesDecisionId` pointing back to the original, instead of transitioning it to `Revised`.
- CI (`.github/workflows/decision-engine-ci.yml`) runs `npm ci`, `npm run typecheck`, and `npm test` on every PR touching this package.
